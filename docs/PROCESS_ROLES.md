# 개발 프로세스와 역할 정의 — MeterialFiles

**생성**: 2026-10-28, FSS-team-bootstrap. 이 문서는 뼈대다 — 프로젝트에서 실제로 겪은 일에 맞춰 고쳐 쓴다.
**구성**: 0~12장은 공통, 부록은 켜진 선택 장만 있다 (S 규격 준수).

---

## 0. 원칙

- 오너(사용자)가 최종 의사결정권자다. 3회 규칙(3장)에 걸리는 사안은 오너와 협의한 뒤 다시 시작한다.
- **일정·작업의 단일 진실원은 GitHub**(curtana/MaterialFiles)이다. 요구사항 하나 = 이슈 하나, 릴리스 버전 하나 = 마일스톤 하나(`v<X.Y.Z>`). 요구사항 정리·영문 작업지시서는 이슈 코멘트로, 설계 문서는 git(`docs/design/`)에 둔다.
- **모든 병합은 PR로 한다** — design·feature → develop, develop → master 모두. 로컬 `git merge`로 develop·master에 넣지 않는다. 이 저장소는 포크라 `gh`에는 `--repo curtana/MaterialFiles`를 붙인다(상위 저장소로 PR이 가는 것을 막는다). 저장소는 공개라 이슈·PR·문서에 비밀값·개인 정보를 쓰지 않는다.
- 실행 구조: PM(매니저) = 메인 세션(Claude), 나머지 역할 = 규칙과 도구 제한이 걸린 서브에이전트(7장). 오너가 부르는 "감독관"·"관리자"·"PM"은 매니저와 같은 사람이다.
- **팀 구조**: 모든 소통이 PM을 거칠 필요는 없다 — 설계팀·개발팀은 검수팀을 직접 부르고, 개발팀·검수팀은 설계팀에 직접 문의하며, 검수 왕복은 자율로 돈다. PM은 요구사항 정리, 단계 전환·머지 승인, 3회 규칙 에스컬레이션 수신, 오너 결정 요청, 병합·릴리스 게이트 같은 **상위 판단**에 집중한다. 배포관은 PM만 부른다.
- 매니저·오너는 언제든 작업을 일시 정지할 수 있다(8장).
- 언어·런타임: Kotlin (Android, Gradle). 오너 터미널: PowerShell(오너에게 주는 명령은 이 문법으로).

## 1. 역할과 권한 요약

| | 설계 문서 | git 쓰기 | GitHub | 이슈·마일스톤 |
|---|---|---|---|---|
| **PM(매니저)** | 읽기·승인 | 문서·설정(팀 구조) | PR 머지, 코멘트 | 관리(생성·마일스톤·라벨) |
| **설계팀** (`designer`) | SRS·HLD 작성, 릴리스 문서 동기화·CHANGELOG | `design/` 브랜치, feature 브랜치의 `docs/design/`만 | 설계 PR, 코멘트 | PM에게 요청 |
| **개발팀** (`developer`) | LLD 작성, SRS·HLD 읽기 | `design/` 브랜치의 LLD, feature 브랜치 | feature PR, 영문 작업지시서 코멘트 | PM에게 요청 |
| **검수팀** (`reviewer`) | 읽기(검수) | **금지**(전용 워크트리에서 실행만) | PR·이슈 코멘트(기록 수단) | PM에게 요청 |
| **배포관** (`releaser`) | 읽기 | release 브랜치 분기·태그만 | develop→master PR 생성·머지, 릴리스 | 마일스톤 닫기 |
| **분석가** (`analyst`) | 읽기 | **금지**(`_workspace/analysis/`만) | — | — |

## 2. 역할 상세

### 2-1. PM — 매니저 (메인 세션)
- 사용자 요구사항을 받아 이슈를 만들고(마일스톤 `v<X.Y.Z>` 지정, 없으면 만든다) **요구사항 정리**([templates/REQUIREMENTS.md](templates/REQUIREMENTS.md))를 이슈 코멘트로 올린 뒤 설계팀을 부른다. 개정은 새 버전 코멘트로(구버전 수정 금지). 오너에게 물어야 할 점이 있으면 정리 단계에서 먼저 묻는다.
- 단계 전환을 결정한다: SRS·HLD 통과 → 개발팀(LLD) 호출, LLD 통과 + 영문 작업지시서 승인 → 설계 PR 머지 → 개발팀(구현) 호출, 코드 검수 통과 → feature PR 머지.
- 재작업 횟수를 이슈 코멘트로 센다(**카운트 주체는 PM뿐**). 3회 규칙에 걸리면 조율하고, 방향이 갈리면 오너에게 결정을 받는다.
- 머지는 PR로 PM이 한다(`gh pr merge <PR> --repo curtana/MaterialFiles --merge`). 검수팀이 저장소를 바꾸지 않았는지 사후에 `git status`·`git log`로 확인한다.
- **자기 규율**: 서브에이전트는 격리된 워크트리에서 일하지만 매니저는 공유 메인 트리를 직접 쓴다 — 실제 사고 위험은 매니저 쪽에 있다. 파일을 직접 고치기 전, 배포관 호출 직후에는 `git branch --show-current`로 브랜치를 확인한다.
- 서브에이전트의 "완료·정리했다" 보고는 검증되지 않은 주장이다 — 9-4 잔여 점검을 직접 다시 돌린다. 서브에이전트가 돌고 있다고 말하기 전에 `ListAgents`로 실제로 도는지 확인한다(중첩 호출 체인은 조용히 멈출 수 있다).

### 2-2. 설계팀 (`.claude/agents/designer.md`)
- 요구사항 정리로 **SRS**([templates/SRS.md](templates/SRS.md))를 써서 검수받고, 통과한 SRS로 **HLD**([templates/HLD.md](templates/HLD.md))를 써서 검수받아 보강한다. 브랜치는 `design/<이슈>-<주제>`, 문서는 `docs/design/<이슈>-<주제>/`, 언어는 한국어.
- 개발팀·검수팀의 문의에 답하고 필요하면 SRS·HLD를 고친다(변경 이력 + 바뀐 절 재검수). 요구사항 자체가 바뀌는 변경은 PM에게 올린다.
- 릴리스 준비 때 문서를 소스·상태와 동기화하고 `CHANGELOG.md`에 버전 절을 쓴다(5장).
- 코드는 수정하지 않는다.

### 2-3. 개발팀 (`.claude/agents/developer.md`)
- **LLD**: SRS·HLD로 **함수 중심 LLD**([templates/LLD.md](templates/LLD.md))를 같은 설계 브랜치에 써서 검수받는다. 설계와 어긋나면 설계팀에 피드백한다(SRS·HLD는 직접 고치지 않는다).
- **영문 작업지시서**: LLD가 통과하면 그것으로 영문 작업지시서([templates/TASK_ORDER.md](templates/TASK_ORDER.md))를 쓴다. PM 승인 뒤 이슈 코멘트로 게시한다.
- **구현**: develop에서 `feature/<이슈>-<주제>`를 분기해 구현과 검증 코드(테스트)를 쓰고 develop 대상 PR을 만든다. 완료된 코드·검증 코드·중요사항을 PR에 적어 검수팀을 직접 부르고, 반려↔수정 왕복을 스스로 반복한다. 통과 확정 뒤 PM에게 최종 보고한다. 머지는 PM.
- 같은 주제가 3회 반복되면 즉시 멈추고 PM에게 보고한다(3장).

### 2-4. 검수팀 (`.claude/agents/reviewer.md`, 개발팀과 다른 모델)
- 설계 문서(SRS·HLD·LLD·릴리스 문서 동기화)와 코드를 검증한다. 코드는 영문 작업지시서·LLD와 대조하고 테스트(CI 결과 + 바뀐 모듈 테스트)를 직접 돌린다.
- **절대 코드·문서를 수정하지 않는다**: 소스·문서 수정과 저장소를 바꾸는 git 명령 금지. 빌드·테스트·가설 실험은 **자기 전용 워크트리**(`G:\tmp\MeterialFiles\review-pr<PR>`)에서 하고 끝나면 지운다.
- 설계 의도가 문서로 판단되지 않으면 설계팀에 문의하고 답을 검수 기록에 남긴다.
- PR 커밋 기준으로 검수하고, 결과는 심각도와 `[기계]`/`[판단]`(11-3)을 붙여 PR 코멘트와 `_workspace/review/`에 남긴다 — PM 중계 없이 왕복이 여러 번 일어나도 이 기록으로 재구성할 수 있어야 한다.

### 2-5. 배포관 (`.claude/agents/releaser.md`, 가벼운 모델)
- PM의 요청으로만 develop→master PR 병합, release 브랜치 분기, 태그·릴리스·빌드, 마일스톤 닫기를 한다. 실패하면 **고치지 않고** 진단만 보고한다(수정 task는 PM이 개발팀에게).
- 릴리스 노트는 `CHANGELOG.md`의 그 버전 절을 그대로 쓴다. 절이 없으면 멈춘다.
- 빌드 산출물은 로컬 SHA256과 릴리스 자산 digest를 직접 대조한 뒤에만 완료로 본다.

### 2-6. 분석가 (`.claude/agents/analyst.md`)
- 새 입력 데이터의 품질·수집 절차 문제를 찾는다. 코드는 읽고 실행만 한다. 결과는 `_workspace/analysis/`. 코드 수정·이슈 등록은 매니저 판단.

## 3. 3회 규칙

- **단위**: 이슈 안의 **같은 주제** — 같은 단계(SRS·HLD·LLD·코드·릴리스 문서)의 같은 지적, 같은 설계 쟁점의 문의·피드백 왕복, 같은 배포 실패. 그 재작업(검수 반려→수정, 설계 피드백→수정, 배포 실패→재시도, 같은 결함 재발)을 센다.
- **기록**: 재작업마다 PM이 이슈에 `재작업 N회차 (<단계>: <주제>)` 코멘트를 남긴다.
- **발동**: 같은 주제로 3회째 재작업이 생기는 순간 작업을 멈추고 PM에게 보고한다. PM이 조율하고(지시·문서 정리, 역할 간 쟁점 판정), 방향이 갈리면 이슈에 `오너협의` 라벨을 붙여 오너에게 결정을 받는다. 결정을 이슈에 기록한 뒤 다시 시작한다.
- **조기 에스컬레이션**: 다음 중 하나면 3회를 기다리지 않고 재작업을 멈추고 매니저에게 올린다 — 같은 방식으로 한 번 더 돌려도 결과가 달라질 근거가 없다.
  1. **같은 실패가 2회 연속** — 같은 테스트ID·같은 검수 지적(파일·함수 기준)이 두 라운드 연속으로 나온다.
  2. **라운드 전후 diff가 그대로** — 재작업 뒤 커밋이 그대로이거나 직전 라운드 대비 `git diff --stat`이 비어 있다.
  3. **실패 책임이 개발자가 아님** — 11-4 `owner`가 `manager`(지시서·설계 결함) 또는 `golden`(기대값·환경)이다.
  조기 에스컬레이션도 회차 코멘트에 사유(1·2·3)와 함께 기록한다. 매니저는 지시서를 고치거나(→ 회차를 새로 센다) 오너 협의로 넘긴다.
- **'기준 자체 재검토' 항목**: 3회째 검수 보고와, 매니저가 오너·이슈에 올리는 3회째(또는 조기 에스컬레이션) 보고에는
  결함 내용과 별도로 **기준이 맞는지**를 적는다 — 지시서 DoD가 달성 가능한가, 검수 기준이 변경 의도와 맞는가,
  환경 전제가 맞는가. 근거를 대고 모르면 "미확인". 기준을 바꾸자는 결론은 제안일 뿐이며 실패를 통과로 바꾸는 근거로 쓰지 않는다.

## 4. 검수 필수 기준

| 구분 | 검수 |
|---|---|
| 설계 문서 SRS·HLD·LLD, 릴리스 문서 동기화·CHANGELOG | **필수**(단계마다) |
| file system backend (app/src/main/java/me/zhanghai/android/files/provider/), file jobs (filejob/), JNI (app/src/main/jni/), build config (app/build.gradle) | **필수** |
| 오너 확인 지점이 걸린 이슈 | **필수** |

| 오탈자·링크 같은 문서 잡무 | 작성자 자가 확인으로 충분 |

## 5. 표준 작업 흐름

### 5-1. 개발 (요구사항 하나)

```
오너: 요구사항
→ PM: 이슈 생성(마일스톤 v<X.Y.Z>) + "📌 요구사항 정리" 코멘트 → 설계팀 호출
→ 설계팀: design/<이슈>-<주제> 브랜치, 설계 PR(draft, develop 대상)
    SRS.md → 검수팀(SRS) ↺ 수정
    HLD.md → 검수팀(HLD) ↺ 보강
  → PM에게 SRS·HLD 통과 보고
→ PM: 개발팀 호출(LLD)
→ 개발팀: 같은 설계 브랜치에 LLD.md(함수 중심) → 검수팀(LLD) ↺ 수정
    ↳ SRS·HLD와 어긋나면 설계팀에 피드백 → 설계팀이 SRS·HLD 수정 → 바뀐 절 재검수
  → LLD 통과 → 영문 작업지시서 초안을 PM에게
→ PM: 작업지시서 승인 → 설계 PR 머지(develop) → 개발팀이 "📋 Work Order"를 이슈에 게시
→ PM: 개발팀 호출(구현)
→ 개발팀: develop에서 feature/<이슈>-<주제> 분기, 구현 + 검증 코드 → develop 대상 PR
    PR에 완료 코드·검증 코드·중요사항 → 검수팀(코드) ↺ 수정
    ↳ 검수팀·개발팀은 필요하면 설계팀에 문의·확인 (설계 수정은 이 feature 브랜치의 docs/design/에)
    ↳ 검수팀은 코드를 고치지 않고, 전용 워크트리에서만 검증
  → 검수 통과 → PM에게 최종 보고
→ PM: feature PR 머지(develop) → 이슈 닫힘(PR의 Closes #<이슈>)

어느 단계든 같은 주제 3회 → 멈추고 PM 보고 → PM 조율, 필요하면 오너 결정(3장)
```

### 5-2. 병합 요청 (오너가 "병합"을 요구할 때)
PM → 배포관: develop→master **PR** 생성·머지 → 결과 보고. 릴리스는 하지 않는다.

### 5-3. 릴리스 요청 (오너가 "릴리스"를 요구할 때)
1. PM: 마일스톤 `v<X.Y.Z>`의 열린 이슈를 확인한다 — 남은 것은 다음 마일스톤으로 옮기거나 오너에게 묻는다. 진행 중인 묶음은 끝낸 뒤 릴리스한다(12장).
2. PM → 개발팀: `app/build.gradle`의 `versionCode`·`versionName`을 올리는 작은 PR(develop 대상, 검수 자가 확인).
3. PM → 설계팀: `design/release-v<X.Y.Z>` 브랜치에서 **문서를 소스·상태와 동기화**하고 `CHANGELOG.md`에 버전 절([templates/CHANGELOG_ENTRY.md](templates/CHANGELOG_ENTRY.md))을 쓴다 → 검수팀(릴리스 문서) → PM이 PR 머지(develop).
4. PM → 배포관: develop→master **PR** 머지 → `origin/master`에서 `release/v<X.Y.Z>` 분기 → 태그 `v<X.Y.Z>` → GitHub 릴리스(노트 = CHANGELOG 그 절) → APK 빌드·첨부·해시 대조 → 마일스톤 닫기 → 결과 보고.
   CHANGELOG는 develop→master를 거쳐 release 브랜치에도 들어 있다(release에 직접 커밋하지 않는다).

### 5-4. 브랜치 모델

| 브랜치 | 분기 원점 | 들어가는 방법 | 비고 |
|---|---|---|---|
| `design/<이슈>-<주제>` | develop | 설계팀(SRS·HLD)·개발팀(LLD) 커밋 | 설계 PR(develop 대상). 영문 작업지시서 승인 뒤 PM이 머지 |
| `design/release-v<X.Y.Z>` | develop | 설계팀 커밋 | 릴리스 문서 동기화·CHANGELOG. develop 대상 PR |
| `feature/<이슈>-<주제>` | develop | 개발팀 커밋(설계 수정 시 설계팀의 `docs/design/` 커밋) | develop 대상 PR로만 합친다 |
| `develop` | — | design·feature PR 머지(PM) | 직접 커밋 금지 |
| `master` | — | develop→master PR 머지(배포관) | 직접 커밋 금지 |
| `release/v<X.Y.Z>` | master | 배포관이 분기 | 버전마다 하나. 태그·빌드는 여기서. **직접 커밋 금지** — 수정은 feature→develop→master를 거쳐 새 버전 release로 |

PM이 반드시 개입하는 지점: ① 요구사항 정리·오너 확인 ② 단계 전환(LLD 착수·작업지시서 승인·구현 착수) ③ 모든 PR 머지 ④ 3회 규칙 조율·오너 결정 ⑤ 병합·릴리스 게이트.
구현 단계의 반복은 워크플로 `.claude/workflows/dev-verify.js`(`Workflow({ name: 'dev-verify', args: { issue: <번호> } })`)로 돌릴 수 있다 — 승인된 영문 작업지시서 → 구현 → 검수 → 최대 3회. 설계 단계(SRS·HLD·LLD)는 워크플로 없이 역할 호출로 진행한다.

## 6. 검수 이력 관리

- 검수 요청·결과는 해당 PR(또는 이슈)에 코멘트로 남긴다: 검수 대상(SRS·HLD·LLD·코드·릴리스), 범위, 강조점, 발견 사항(심각도), 조치 결과, 설계팀 문의와 답.
- 상세는 `_workspace/review/pr<번호>_<대상>[_회차N].md`(git 제외).
- 설계 문서의 변경 이력은 각 문서의 "변경 이력" 표에 남긴다(git 이력과 별개로 사유·요청자를 남긴다).

| 역할 | 정의 | 모델 | 도구 |

| PM(매니저) | 메인 세션 | 기본 | 전체 |

- **하위 Agent 호출은 반드시 `run_in_background: false`**: 서브에이전트가 자기 안에서 비동기로 다른 에이전트를 부르면 자식의 완료 알림은 최상위(매니저)에게만 간다. 부른 쪽은 재개되지 못하고 작업이 방치된다.
- 도구 제한으로 검수자의 파일 쓰기는 막히지만 Bash를 통한 git 조작은 기계적으로 막을 수 없다 → 지시서 금지 규칙 + 매니저의 사후 검사로 보강한다. 누가 누구를 부를 수 있는지도 지시서 규칙으로 강제한다 — 설계팀·개발팀 → 검수팀, 개발팀·검수팀 → 설계팀(문의), 배포관은 PM만.
- 설계팀은 코드를 고치지 않는다는 규칙도 후크가 아니라 지시서 규칙이다(문서 쓰기가 필요해 경로 제한 역할에 넣지 않았다) — 검수팀이 설계 PR의 바뀐 파일이 `docs/`·`CHANGELOG.md`뿐인지 확인한다.
- 보조 에이전트(code-reviewer·change-verifier)는 매니저가 가볍게 쓰는 수단이며 정식 검수를 대체하지 않는다.
- 새 전문 역할이 필요하면 매니저가 `.claude/agents/`에 정의를 추가하고 이 표를 고친다.

## 8. 일시 정지 (매니저·오너 전용)

- **전체 정지 — `WORK_HOLD` 파일**: 저장소 루트에 있으면 모든 역할은 새 작업을 시작하지 않고, 진행 중인 작업은 안전한 지점(커밋·보고)까지만 마무리한다. 파일에 지시자·일시·사유·재개 조건을 적는다. 오너는 GitHub 웹에서 파일을 추가·삭제해 세션 밖에서도 멈출 수 있다. 각 역할은 시작 전 `git pull` 후 확인한다.
- **이슈 단위 정지 — `일시정지` 라벨**: 그 이슈만 멈춘다. 해제는 라벨 제거.

## 9. 실행 환경과 실행 통제

배경: 입력 없는 python REPL 하나가 64분간 5.4 GB를 쓰며 살아 있었고, 보고에는 "바로 종료했다"고 적힌 사고가 있었다. 지시만으로는 막지 못해 **기계적 통제(후크)와 기계 확인(잔여 점검)**을 둔다. 효율을 해치지 않도록 오너 승인 요청은 꼭 필요한 곳에만 두고, 위험한 형태는 승인 대신 차단한다.

### 9-1. 실행 환경 사실
- **에이전트의 Bash·PowerShell에는 대화형 입력이 없다.** 입력을 기다리는 것(python REPL, `input()`, `Read-Host`, 페이저, 편집기, 메시지 없는 `git commit`, `git … -i/-p`, 확인 프롬프트가 있는 설치)은 멈추거나 폭주한다.

### 9-2. 파이썬 정책
| 주체 | 허용 | 금지 |
|---|---|---|
| 매니저 | venv python만(`/g/workspace/MeterialFiles/venv/Scripts/python.exe`)의 스크립트·`-c`·`-m`. 시스템 python은 venv를 만들 때만 | 시스템 python으로 작업 실행, REPL 형태(`python` 단독·`-i`), `python -`(heredoc·파이프 입력 포함) |
| 서브에이전트 | venv python만: `/g/workspace/MeterialFiles/venv/Scripts/python.exe`(Git Bash) / `G:\workspace\MeterialFiles\venv\Scripts\python.exe`(PowerShell) | 시스템 python, REPL 형태 |

- venv는 메인 체크아웃의 `venv/`(git 제외) 하나를 모든 역할·워크트리가 같이 쓴다. 없으면 `python -m venv venv`로 만든다. 패키지가 필요하면 라이브러리 승인(10장)을 거쳐 이 venv에 설치한다.
- 후크는 서브에이전트의 시스템 python만 기계적으로 거부한다. 매니저의 venv 사용은 규칙으로 지킨다.

### 9-3. 후크 — `.claude/tools/hook_guard.py`
후크 입력에는 서브에이전트가 실행한 도구 호출에만 `agent_id`가 붙는다 — 이것으로 매니저와 서브에이전트를 구분한다. 연결은 `.claude/settings.local.json`(git 제외)에 있다.

| 모드 | 하는 일 |
|---|---|
| `pretool` | 실행 전 거부: 입력을 기다리는 형태(누구든), 서브에이전트의 시스템 python, reviewer·analyst의 `_workspace/` 밖 Write·Edit. 거부 사유에 대안을 적어 돌려준다. matcher는 `Bash\|PowerShell\|Write\|Edit\|MultiEdit\|NotebookEdit`. |
| `substop` | 서브에이전트 종료 시 남긴 실행 중 작업을 `_workspace/hooks/agent_background.jsonl`에 기록하고 경고한다. **종료를 막지 않는다** — 막아도 정리 지시가 전달되지 않고, bash 안의 자식은 고아로 남는다. 고아는 9-4가 찾는다. |
| `approval` | 승인 요청을 `_workspace/hooks/approvals.log`에 기록만 한다. |

**역할별 Write·Edit 경로 제한**: `agent_type`이 reviewer·analyst이면 Write·Edit·NotebookEdit는 **메인 저장소 `_workspace/` 안**에서만 허용한다. 워크트리 안의 `_workspace/`, 저장소 코드·문서, 임시 폴더는 거부한다(지워도 되는 임시 파일은 Bash로). 상대 경로는 후크 입력 `cwd` 기준으로 풀고, 못 풀면 거부한다. 다른 역할·매니저는 제한 없다. 역할 목록은 `team.config.json`의 `workspace_only_roles`(없으면 켠 모듈에서 정함).

- 거부·경고 기록: `_workspace/hooks/guard.log`. 후크 자체 오류는 절대 명령을 막지 않는다(fail-open).
- 후크 명령은 메인 체크아웃의 `hook_guard.py`를 가리킨다 — 규칙을 바꾼 PR은 메인 체크아웃이 그 커밋을 받아야 적용된다.
- 권한 규칙의 와일드카드는 접두사 비교라 `Bash(python - *)`는 `python -c`까지 막는다 — 정밀 판정은 후크에 둔다. 권한 `deny`에는 `python`·`python -` 단독 형태만 둔다.

### 9-4. 잔여 점검 — `bash .claude/tools/check_leftovers.sh <작업명> [--tasks-dir <폴더>]`
읽기 전용. ① 이 프로젝트 python 프로세스·REPL 형태 python ② 세션 tasks 폴더 `b*.output` 100 MB 초과·계속 증가 ③ 그 작업의 감시자 프로세스 ④ `G:\tmp\MeterialFiles\*<작업명>*` 잔존(경고) ⑤ 서브에이전트가 남긴 백그라운드 명령의 고아 프로세스. 마지막 줄 `LEFTOVERS: none` / `LEFTOVERS: <n> found`.
- **서브에이전트는 완료 보고에 이 출력을 붙인다.** 매니저는 완료 보고를 받으면 같은 스크립트로 다시 확인한다. 고아는 명령줄·시작 시각으로 소유를 확인한 뒤에만 정리한다(같은 PC의 다른 세션 프로세스는 건드리지 않는다).

### 9-5. 장시간 명령
- `timeout <예상 시간의 2배>`로 감싸고 출력은 파일로 받는다.

### 9-6. 알려진 한계
- 후크는 Bash·PowerShell 명령 문자열과 Write·Edit 대상 경로만 본다. 스크립트 안에서 띄운 하위 프로세스는 9-4로 사후에 찾는다.
- **후크는 fail-open이다**: 입력 해석 실패·예외·시간 초과면 아무것도 막지 않는다. 후크가 통과시켰다고 허용된 것이 아니다 — 규칙 자체를 지킨다.
- **스크립트 내부 쓰기는 못 잡는다**: 스크립트(`.py`·`.ps1`·`.sh`)가 안에서 보호 데이터에 쓰거나, 제한 역할이 Bash(`sed -i`·`cp`)로 저장소 파일을 고치는 것은 막지 못한다. 명령 판정도 보수적 근사라 변수 간접 참조(`D=<보호경로>; rm -rf $D`)·별칭은 놓칠 수 있다. 저장소 변경은 검수자의 `git status`로 확인한다.
- 자동 모드 분류기는 "거부 직후 다른 경로로 재시도"를 우회로 보고 막을 수 있다 → 서브에이전트에는 처음부터 허용된 경로를 쓰라고 지시한다.

## 10. 자율 진행 기준과 라이브러리 승인

| 구분 | 내용 |
|---|---|
| 묻지 않고 진행 후 보고 | 결과를 바꾸지 않는 PR(문서·시험·도구)은 검수 통과 시 머지까지, 승인된 계획의 다음 단계 착수, 매니저 자신의 임시 워크트리·폴더 정리 |
| 계속 묻기 | 요구사항 범위·사용자에게 보이는 동작의 결정, 결과를 바꾸는 변경, 규격 해석·편차 등록, develop→master 병합과 릴리스(오너의 명시적 요구가 있을 때만), 외부 공개·영구 삭제, 권한·설정을 완화하는 변경 |

- 자동 모드 분류기가 막으면 우회하지 말고 한 줄로 알린다.
- **라이브러리 승인**: 개발자가 필요 라이브러리와 사유를 요청 → 매니저가 라이선스·크기·유지보수성을 보고 결정, 이슈에 기록 → 개발자가 설치하고 의존성 파일을 같은 PR에서 갱신.

## 11. 작업 규율 — 근본 원인·증거·리뷰 분류·보고 형식

결과값을 바꾸는 규칙이 아니라 일하는 방식의 규칙이다.

### 11-1. 근본 원인 먼저 (버그·불일치 수정)
원인을 확인하기 전에는 고치지 않는다. 증상만 고치면 다음 버그를 찾기 더 어려워진다.
1. **증상 수집·재현**: 결정적으로 재현되지 않으면 증거를 더 모은다.
2. **최근 변경 확인**: `git log --oneline -20 -- <관련 파일>`. 예전에 맞았다면 원인은 그 사이 diff에 있다.
3. **처리 단계별 확인**: 입력(데이터) 탓으로 결론 내기 전에 같은 입력을 처리 단계별로 따라가 어디서 갈라지는지 찾는다.
4. **가설 한 문장**: "원인 가설: …"을 적고 임시 로그·assert로 확인한다. 확인 전에 수정안을 쓰지 않는다.
5. **최소 수정 + 회귀 테스트**: 회귀 테스트는 수정 전 코드에서 실패하고 수정 후 통과함을 실제로 확인한다.
- 가설 3개가 연달아 틀리면 멈추고 매니저에게 보고한다. 수정이 5개 파일을 넘으면 착수 전에 범위를 알린다.
- 경고 신호: "일단 임시로 고치자", 데이터 흐름을 따라가기 전의 수정안, 고칠 때마다 다른 곳이 터짐, 같은 파일에서 버그가 되풀이됨.

### 11-2. 증거 없는 완료 금지 (전 역할)
- "완료·통과·불변·정리됨"에는 **이번에 실행한** 명령과 출력 끝부분을 붙인다. 검증 뒤 코드가 바뀌면 다시 돌린다(주석·문서만 바뀐 경우 제외).
- "될 겁니다", "확신합니다", "아까 테스트했습니다", "사소한 변경입니다"는 증거가 아니다. 검증할 수 없는 것은 "미확인"으로 적는다.

### 11-3. 리뷰 발견 분류와 근거 없는 "괜찮다" 금지 (검수자 → 개발자)
| 표시 | 대상 | 처리 |
|---|---|---|
| `[기계]` | 죽은 코드·안 쓰는 변수, 낡은 주석, 매직넘버→상수, 오타, 경로·버전 불일치 | 개발자가 묻지 않고 반영 |
| `[판단]` | 결과를 바꿈, 기능·출력 항목 제거, 사용자에게 보이는 동작 변경, 규격 관련, 20줄 초과 수정, 의견이 갈리는 것 | 매니저 결정(결과 변경은 10장에 따라 오너) |

- "안전하다" → 근거 줄(파일:줄), "다른 곳에서 처리된다" → 처리 코드, "테스트가 있다" → 테스트 이름. 못 대면 "미확인".
- 새 상수·열거값이 생기면 형제 값을 grep해 diff 밖 사용처까지 읽는다.
- 지적하지 않는 것: 임계값 이유 주석 요구, 무해한 중복, 일관성만을 위한 변경, diff 안에서 이미 해결된 것.

### 11-4. 보고 마지막 줄 JSON
보고 본문은 각 역할 정의대로 두고, **응답의 마지막 줄**에 JSON 한 줄을 붙인다(코드 블록 없이). 매니저는 이 줄로 상태를 먼저 판단하고, 없거나 깨졌으면 본문을 읽는다.
`status`: `DONE`(증거 있음) / `DONE_WITH_CONCERNS`(확인 못 한 부분 명시) / `BLOCKED`(사유·시도·권고) / `NEEDS_CONTEXT`(되묻기). 역할별 필드는 각 에이전트 정의에 있다. 워크플로처럼 출력 스키마를 지정해 부르면 그 스키마가 우선이다.

검수 보고 JSON에는 공통으로 `owner`와 `repeat2`를 둔다.
- `repeat2`: 직전 라운드와 같은 실패(같은 테스트ID·같은 지적)가 다시 나왔으면 `true` — 3장 조기 에스컬레이션 1.
- `owner`(실패·반려·조건부일 때 필수, 통과면 `null`): **이 실패를 누가 풀어야 하는가.** 섞이면 개발자가 아닌 쪽을 적고 본문에 발견별로 나눈다.

| `owner` | 뜻 | 예 | 다음 행동 |
|---|---|---|---|
| `developer` | 구현·LLD 결함 — 지시서·LLD대로 고치면 풀린다 | 로직 오류, 빠진 처리, 테스트 미작성, LLD 함수 명세 누락 | 개발팀 재작업 |
| `designer` | SRS·HLD 결함 — 설계 문서를 고쳐야 풀린다 | 요구가 SRS에서 빠짐, HLD 추적 누락, 문서 간 모순 | 설계팀 수정(바뀐 절 재검수) |
| `manager` | 지시서·설계 결함 — 지시서대로 하면 이 실패가 난다 | 지시서 모순, DoD 달성 불가, 범위 밖 결정 필요 | **재작업 없이** 매니저에게(지시서 수정·오너 협의) |
| `golden` | 기대값·환경 문제 — 코드와 무관하게 실패한다 | 기대값이 이전 결정과 어긋남, 데이터 누락, 실행 환경·CI 문제, 기준 커밋에서도 같은 실패 | **재작업 없이** 매니저에게(개발자가 기대값을 고쳐 통과시키지 않는다) |

- 근거(파일:줄·이슈 결정·기준 커밋 재현)를 본문에 붙인다. 근거 없이 `manager`·`golden`으로 미루지 않는다(11-3).
- 개발자도 지시서 결함으로 막히면 `"status":"BLOCKED"`로 하고 본문에 `owner: manager` 사유를 적는다.
- dev-verify 워크플로 스키마에도 `owner`·`failure_ids`(라운드 간 비교용)·`criteria_review`(3회째)가 있고, 3장의 세 조건이면 재작업 없이 `escalated`로 반환한다.

## 12. 매니저 작업 원칙

오너와 일하면서 확립된 방식이다. 프로젝트에서 새로 생기는 원칙은 여기에 덧붙인다.

- **뻔한 선택엔 승인을 요청하지 않는다.** 대안이 없는 사항(이미 정한 작업 폴더의 하위 경로 등)은 그냥 진행한다. 무조건 승인할 수밖에 없는 질문은 소음이다. 진짜 정책상 승인 대상과 섞지 않는다.
- **형식적 절차를 붙이지 않는다.** 변경의 위험(결과 경로를 건드리는가)을 먼저 보고 필요한 확인만 한다. 상수·문서 PR에 CI 대기·전체 재테스트를 붙이지 않는다. 대신 되돌리기 어려운 외부 행위(태그·릴리스·배포)의 오너 확인과 해시 대조는 그대로.
- **진행 중인 묶음을 끝낸 뒤 릴리스한다.** 착수한 작업을 두고 중간 릴리스를 끊지 않는다.
- **짧은 작업은 바로 끝낸다.** 서브에이전트를 기다리는 동안 손 놓지 말고 직접 확인할 수 있는 것을 병행한다. 분리한 세션은 독립 작업이다 — 다른 세션 작업을 기다리게 만들 일이면 애초에 분리하지 않는다.
- **오너에게 일을 맡길 때는 정확히** 지시한다 — 단계·대상·동작·금지·이유·확인법. 매니저가 할 수 있는 일은 직접 하고, 오너에게는 결정과 매니저가 할 수 없는 일만 요청한다.
- **문제가 있어도 통보하고 막지 않는 것이 사용자 기능의 기본값이다.** 사용자의 선택을 UI에서 미리 차단하지 않는다. 계산이 불가능하면 실행 시점에 실패를 분명히 알린다. 예외는 오너에게 먼저 묻는다.
- **악용·변조 방어 코드는 기본 보류한다.** 사용자가 입력을 일부러 고쳐야만 생기는 사례까지 막으려 하면 방어할 예가 끝없이 늘어난다. 정상 입력 경로의 결함만 고친다.
- **임시 파일은 `G:\tmp\MeterialFiles\<작업명>`에만** 만들고 끝나면 지운다. 남길 결과는 `_workspace/`.
- **보고 형식**: 그래프가 있으면 PDF, 표·글 위주면 md 파일로 남기고 링크를 준다. 결과 전달 시 시각은 현지 시각으로, 브랜치·병합 여부를 분명히 적는다.

## 부록 S. 규격 준수 — Android app quality guidelines (Core App Quality + Play policy)

이 프로젝트는 Android app quality guidelines (Core App Quality + Play policy)을 지켜야 한다. **규격은 적합도를 겨루는 후보가 아니라 먼저 지켜야 할 조건이다.** 다른 도구·과거 결과와 값이 맞는지는 규격을 지킨 뒤에 보는 참고일 뿐이다.
- 설계 문서마다 "규격 근거" 절을 둔다: 조항 번호, 요지, 필수/권장, 충족 방법. 원문 문장은 옮기지 않고, 근거 자료에 없는 조항은 추측하지 않고 "원문 판독 필요"로 둔다.
- 규격에서 벗어나는 결정은 편차 등록부에 올리고 오너 승인을 받은 뒤에만 머지한다.
- 결과 로직을 바꾸는 PR은 추적표(`docs/STANDARDS_TRACEABILITY.md`)를 같은 PR에서 고친다. 검수자는 빠졌으면 반려한다.
- **결과를 바꾸는 변경은 규격이 요구할 때만**, 그때도 규격을 만족하는 최소 변경으로 한다. 규격 때문에 결과가 바뀌는 작업은 미루지 말고 다음 릴리스 전에 한다.
- 조항 해석은 오너 승인 사항이다. 다만 프로그램 동작 규칙(파일 우선순위·캐시·입력 처리 예외)은 "규격 요구 아님"으로 매니저가 바로 판단한다.
- 근거 표준의 판과 개정 여부를 등록부에 기록하고 릴리스 전마다 확인한다.
