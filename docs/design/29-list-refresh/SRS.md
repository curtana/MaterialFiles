## 1. 목적과 범위

### 1.1 목적
파일 목록이 이미 보이는 동안 폴더 감시(파일 변경 감지)로 목록을 다시 읽으면 지금은 매번 로딩 표시가 나타난다. 다시 읽기는 `FileListLiveData.loadValue()`가 시작하고(`FileListLiveData.kt:37-62`), 시작할 때 `value = Loading(value?.value)`(`:39`)를 내보낸다. 화면은 `Loading`을 받으면 툴바 부제목을 "Loading…"으로 바꾸고(`FileListFragment.kt:712`, `res/values/strings.xml:25`), 목록이 있으면 당겨서 새로 고침 원형 표시를(`:716`), 목록이 비어 있으면 가운데 진행 표시를(`:717`) 띄운다. 복사·이동 작업 중 원격 파일 시스템은 쓰기마다 변경 알림을 내고(예: SFTP `provider/sftp/client/Client.kt:90`의 `NotifyEntryModifiedSeekableByteChannel`), 감시는 1000ms 간격으로 묶여(`PathObserver.kt:32`, `:61`) 초마다 다시 읽기가 일어난다. 그래서 작업 내내 원형 표시와 부제목이 깜박인다(이슈 #29 B 3).

오너는 "조용한 갱신(B3)"을 골랐다: 목록이 이미 보일 때 감시가 일으킨 다시 읽기는 로딩 표시 없이 목록만 바꾼다. 폴더를 처음 열 때와 사용자가 직접 새로 고칠 때는 지금처럼 로딩 표시를 보인다. 이 문서는 어떤 계기가 조용하고 어떤 계기가 표시를 보이는지, 조용한 다시 읽기가 실패하면 어떻게 되는지를 구현과 수동 확인이 가능할 만큼 정한다.

### 1.2 범위
- 일반 폴더 목록(`FileListLiveData`)의 다시 읽기 계기별 로딩 표시 여부(2.1~2.3).
- 조용한 다시 읽기의 실패 처리와 사용자에게 알리는 방법(2.4).
- 조용한 다시 읽기와 명시 새로 고침이 겹칠 때(2.5).
- 한 창 모드·두 창 모드의 각 창, 감시를 지원하는 모든 파일 시스템(로컬·루트·SAF 문서·콘텐츠·FTP·SFTP·SMB·WebDAV)(2.6).
- 화면 낭독(TalkBack) 사용자에게 주는 정보(2.7, 3.2).

### 1.3 범위 밖
- 이슈 #29의 결함 수정 A1·A2·B1·B2·B6(개발팀 `feature/29-sftp-list-reload`). 이 SRS는 그 수정이 들어간 동작을 전제로 쓴다(4.1 P1~P4).
- B4(원격 파일 시스템의 변경 알림을 줄이거나 감시 간격을 늘리기)와 B5(로딩 표시 지연·최소 표시 시간) — 오너가 제외했다.
- 검색 결과 목록(`SearchFileListLiveData`). 감시가 없어(`SearchFileListLiveData.kt:29-31`, `PathObserver` 없음) 조용한 다시 읽기가 생기지 않는다. 검색 중의 로딩 표시는 지금과 같다.
- 파일 속성 화면(`fileproperties/`), SMB 서버 찾기 화면(`storage/AddLanSmbServerFragment.kt:55`)의 새로 고침. 각자 다른 LiveData를 쓴다.
- 원격 서버에서 다른 프로그램이 바꾼 내용을 감지하는 것. 원격 파일 시스템의 변경 알림은 이 앱이 한 작업에서만 나온다(`provider/common/LocalWatchService.kt:86-98`의 `onEntryCreated/Deleted/Modified`를 각 `Client`가 호출 — 예: `provider/sftp/client/Client.kt:70`, `:90`, `:143-144`). 지금 동작과 같다.

### 1.4 용어
| 용어 | 뜻 |
|---|---|
| 다시 읽기 | 보이는 폴더의 항목 목록을 파일 시스템에서 새로 읽는 한 번의 작업(`FileListLiveData`의 한 번의 목록 읽기, `FileListLiveData.kt:40-61`). |
| 로딩 표시 | 다음 셋을 함께 이르는 말: (1) 툴바 부제목 "Loading…"(`FileListFragment.kt:712`), (2) 당겨서 새로 고침 원형 표시(`swipeRefreshLayout.isRefreshing`, `:716`), (3) 가운데 진행 표시(`binding.progress`, `:717`). 지금 코드에서는 상태가 `Loading`일 때 (1)은 항상(검색 중 제외), (2)는 목록에 항목이 있을 때, (3)은 항목이 없을 때 나타난다. |
| 표시 중인 목록 | 이 창이 지금 보이는 폴더에 대해 마지막으로 받은 항목 목록. 그 폴더의 첫 읽기가 끝난 뒤(성공이든, 이전 목록을 가진 실패든) 존재하며, 빈 폴더의 빈 목록도 "표시 중인 목록"이다. 첫 읽기가 끝나기 전이나 첫 읽기가 실패해 항목 정보가 하나도 없으면(`Failure(null, …)`) 표시 중인 목록이 없다. 코드로는 현재 상태의 `value`가 `null`이 아닌 경우(`util/Stateful.kt`, `FileListLiveData.kt:58`)다. |
| 자동 다시 읽기 | 사용자가 직접 요청하지 않았는데 감시 때문에 일어나는 다시 읽기. 2.1의 T1~T3. |
| 명시 새로 고침 | 사용자의 조작(또는 그 직접 결과)으로 일어나는 다시 읽기. 2.2의 T4~T6. |
| 첫 읽기 | 창이 어떤 폴더를 새로 보이게 될 때의 읽기. 2.3의 T7. |
| 조용한 다시 읽기 | 로딩 표시 셋 중 어느 것도 나타내지 않고, 끝나면 결과만 반영하는 다시 읽기(2.1). |
| 실패 상태 | 마지막으로 끝난 읽기가 실패한 상태(`Failure`). 툴바 부제목이 "Error"(`FileListFragment.kt:711`, `strings.xml:21`)다. |

## 3. 비기능 요구사항

### 3.1 환경·성능
- 지원 API 레벨은 앱과 같다(minSdk 23~). 새 권한·설정·문구를 추가하지 않는다. 문구는 기존 `R.string.loading`·`R.string.error`만 쓴다.
- 조용한 다시 읽기는 다시 읽기 횟수를 늘리지 않아야 한다. 다시 읽기를 언제 몇 번 하는지는 B1·B6(4.1 P1·P3)이 정하고, 이 요구는 표시만 바꾼다.
- 목록 읽기는 지금처럼 작업 스레드에서 하고(`FileListLiveData.kt:40`) UI 스레드에서 무거운 일을 하지 않는다(`Stability_ANR`).
- 루트·비루트, 온라인·오프라인 구분 없이 같은 규칙이다.

### 3.2 접근성
- 새 UI 요소를 추가하지 않으므로 터치 대상·대비·설명 요구는 새로 생기지 않는다.
- 조용한 성공을 알리지 않는 것(REQ-29-13)은 잦은 갱신마다 낭독이 끼어들지 않게 하려는 요구사항 결정이다. 이를 요구하거나 금지하는 조항은 확인한 문서에 없다(5장).

## 4. 제약과 가정

### 4.1 가정 (병행 결함 수정 — 이 SRS는 다시 설계하지 않는다)
가정 번호는 P1~P4로 쓴다(이슈 #29의 결함 이름 A1·A2와 겹치지 않게).
- **P1 (B1)**: 변경 알림은 진행 중인 다시 읽기를 끊지 않는다. 진행 중에 알림이 오면 "다시 읽어야 함"으로 표시해 두고, 그 읽기가 끝난 뒤 한 번 더 읽는다(알림이 여러 번 와도 한 번). 이 뒤따르는 읽기가 T3이다. 명시 새로 고침(T4~T6)은 B1의 대상이 아니며 지금처럼 진행 중인 읽기를 끊고 새로 시작한다고 본다(REQ-29-08). B1 구현이 이와 다르면(예: 명시 새로 고침도 기다리게 함) 설계팀에 알린다.
- **P2 (B2)**: 끊기거나 다른 읽기로 대체된 읽기는 결과(성공·실패 모두)를 화면에 내보내지 않는다. 그래서 REQ-29-06의 "실패"는 실제로 끝까지 실행된 읽기의 실패만 가리킨다.
- **P3 (B6)**: 한 창 모드에서 숨겨진 창은 보이지 않는 동안 다시 읽지 않고, 그동안 변경 알림이 있었으면 다시 보일 때 한 번 읽는다(지금의 `onActive` 경로 `FileListLiveData.kt:64-77`과 같은 모양). 이 읽기가 T2다.
- **P4**: 표시 중인 목록이 있는지는 다시 읽기를 시작하는 순간에 판단한다. T3은 뒤따르는 읽기를 시작하는 순간에 판단한다.

### 4.2 제약
- **C-1**: 결함 수정 A1·A2·B1·B2·B6과 같은 feature 브랜치(`feature/29-sftp-list-reload`)에 B3을 더한다(오너 결정 절차 3). B3 구현은 B1·B2의 구조 위에 얹는다.
- **C-2**: `FileListLiveData.kt`·`FileListFragment.kt`는 상위 저장소 코드다. 바꾸는 줄을 최소로 해 상위 동기화 충돌을 줄인다.
- **C-3**: 사용자에게 보이는 이 규칙(2.8 표)은 오너 확인을 받은 뒤 구현한다(오너 결정 절차 3).

| Q2 | 조용한 다시 읽기 중 당겨서 새로 고침을 하면 진행 중인 읽기를 버리고 새로 읽을까, 진행 중인 읽기의 결과를 기다릴까? | 새로 읽기(REQ-29-08). 사용자가 당긴 시점 이후의 내용을 보장하고, 지금 동작과 같다. |
| Q3 | 실패 상태를 부제목 "Error"보다 더 눈에 띄게(예: 목록 위 막대) 보여야 할까? | 아니오. 새 UI를 만들지 않고 기존 표시(부제목·토스트·빈 목록일 때 가운데 오류 글)를 쓴다. 필요하면 별도 이슈. |

근거는 `docs/STANDARDS_TRACEABILITY.md` v0.6(같은 PR에서 v0.7로 4장에 이 이슈 행 추가)이다. 원문 문장은 옮기지 않았다.
