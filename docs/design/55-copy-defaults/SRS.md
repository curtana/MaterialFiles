## 1. 목적과 범위

### 1.1 목적
지금 복사는 어디로 복사하든 같은 규칙을 쓴다. 링크를 따라가지 않고(`filejob/FileJobs.kt:1354`가 늘 `NOFOLLOW_LINKS`), 백엔드가 권한·수정 시각을 원본에 맞춘다(아래 1.4 표). 오너는 복사를 두 종류로 나눴다(2026-11-04).
- **폰→폰**: `cp`의 기본 동작. 링크는 링크로 복사한다.
- **그 밖의 모든 복사**(방향 무관, 오너: "폰에서 폰으로가 아니면 다 원격이지"): 네트워크의 기본 동작. 속성을 맞추지 않고, 링크를 따라가 대상 내용을 복사한다(폴더를 가리키면 폴더로, 파일을 가리키면 파일로).

이 문서는 그 규칙과, 링크를 따라가며 생기는 실패(대상 없음·순환)와 '바꾸기' 때 기존 데이터를 짐작으로 지우지 않는 규칙을 정한다.

### 1.2 범위
- 복사 작업의 공통 경로 `copy()`(`filejob/FileJobs.kt:949-959`)를 타는 모든 작업: 복사(`CopyFileJob`, 804-), 압축 풀기(같은 클래스, `isExtract`), 다른 이름으로 저장(`SaveFileJob`, 1799), 열기용 캐시 복사(`open`, 1603).
- 위 작업의 사전 집계(`scan`, 269-299)와 충돌 판정(1377-1386) 중 링크를 따라가는지에 따라 달라지는 부분.
- 네트워크 복사의 '바꾸기'에서 기존 대상을 지우기 전의 원본 확인(요구사항 6).

### 1.3 범위 밖
- **이동**(`MoveFileJob`, 1139-): 범위에 넣을지는 오너 질문 Q4(6절). Q4가 정해질 때까지 이 SRS의 요구사항은 이동에 적용하지 않는다.
- **#48**(로컬 xattr 값을 대상에서 읽음): 일시정지. 영향만 적는다(5절).
- 임시 이름으로 쓴 뒤 바꾸기(#42, 오너가 거절). 복사 도중 끊겼을 때의 손실 위험은 #54의 경고로 알리고 그대로 둔다.
- 충돌 창 문구(#54 PR #59). 이 SRS는 #54 파일을 고치지 않는다. 영향은 5절.
- 압축하기(`ArchiveFileJob`), 글 편집기 저장(`WriteFileJob`), #43(루트 원격 프로세스), #21(번역).

### 1.4 현재 코드 (코드 읽기, 실행 안 함)

**복사 작업의 옵션.** `copy()`는 `copyOrMove(…, useCopy = true, copyAttributes = false, …)`를 부른다(`FileJobs.kt:956-958`). 그래서 복사에는 `COPY_ATTRIBUTES`가 없고(1355-1357) `NOFOLLOW_LINKS`만 늘 있다(1354). 이동은 `copyAttributes = true`다(`copyForMove` 1232-1237, `moveByCopy` 1245-1252). 그런데 백엔드 대부분이 `COPY_ATTRIBUTES` 없이도 권한·수정 시각을 맞춘다.

**백엔드 선택.** 원본과 대상의 제공자가 같으면 그 제공자의 `copy`, 다르면 `ForeignCopyMove.copy`가 한다(`provider/common/PathExtensions.kt:47-54`). 그래서 폰↔NAS 사이 전송은 모두 `ForeignCopyMove`를 지난다.

| 경로 | 링크(`NOFOLLOW_LINKS`일 때) | `COPY_ATTRIBUTES` 없이도 맞추는 속성 | '바꾸기' 때 대상 삭제 시점 |
|---|---|---|---|
| 로컬·루트 `provider/linux/LinuxCopyMove.kt` | 링크를 만든다(153-177) | 권한 `chmod`(192-198), 수정 시각(199-211), `user.*` xattr(212-224, #48) | 일반 파일: 원본을 열기 **전**에 지운다(57-66 → 67-71) |
| 공급자 간 `provider/common/ForeignCopyMove.kt` | 링크를 만든다(93-106) | 수정 시각(111-125) | 일반 파일: 원본을 열기 **전**(43-45 → 51). 폴더: 만들기 전(87-89) |
| SFTP `provider/sftp/SftpCopyMove.kt` | 서버에 링크를 만든다(159-183) | 만들 때 권한(68-74, 98, 153), 뒤에 `setstat`로 권한·수정 시각(186-217) | 원본을 열기 **전**(77-86 → 87-91) |
| SMB `provider/smb/SmbCopyMove.kt` | 재분석 지점(링크)을 만든다(114-138) | 수정 시각(146-156) | `copyFile` **전**(75-84 → 85-90) |
| FTP `provider/ftp/FtpCopyMove.kt` | "Cannot copy symbolic links" 실패(56-57) | 수정 시각(106-115) | 원본 종류 확인 **전**(41-45 → 47-57, #56) |
| WebDAV `provider/webdav/WebDavCopyMove.kt` | "Cannot copy symbolic links" 실패(61-62) | 수정 시각(117-) | 원본 종류 확인 **전**(46-50 → 52-62, #56) |
| 문서 제공자(SAF) `provider/document/DocumentCopyMove.kt` | 링크 개념 없음(`DocumentFileSystemProvider.kt:309-312` `readSymbolicLink` 미지원) | 제공자에 맡김 | 복사 **전**(32-42 → 43-51) |
| 압축 파일 `provider/archive/` | 원본으로만 쓰인다. 같은 제공자 안 복사는 읽기 전용 실패(`ArchiveFileSystemProvider.kt:176-180`) | — | — |
| content URI `provider/content/` | 원본으로만 쓰인다. `copy` 미지원(`ContentFileSystemProvider.kt:179-183`) | — | — |

**링크를 따라갈 때 각 백엔드가 하는 일.** `NOFOLLOW_LINKS`를 빼면 각 백엔드는 원본 속성을 따라간 값으로 읽는다: 로컬 `stat`(`LinuxCopyMove.kt:34`), SFTP `stat`(`SftpCopyMove.kt:33`), SMB `FILE_OPEN_REPARSE_POINT` 없이 열기(`SmbCopyMove.kt:33`, `smb/client/Client.kt:341-345`), FTP는 링크를 한 번만 따라간 목록(`ftp/client/Client.kt:257-265`). WebDAV는 따라가기 옵션을 무시한다(`webdav/client/Client.kt:167` "TODO: Support noFollowLinks"). WebDAV의 '링크'는 HTTP 이동 응답이다(`webdav/client/ResponseExtensions.kt:21-22`).

**폴더 순회.** `Files.walkFileTree(source, visitor)`(`FileJobs.kt:836`, `scan` 272)는 링크를 따라가지 않는다. 쓰는 라이브러리(`me.zhanghai.android.retrofile` 1.2.0, `app/build.gradle:208`)의 `FileTreeWalker`는 링크를 따라가는 모드에서 조상 폴더와 `fileKey`(없으면 `isSameFile`)를 비교해 순환을 `FileSystemLoopException`으로 알린다(이번에 `javap`로 `wouldLoop`·`FileSystemLoopException` 사용 확인). 이 비교가 실제 순환을 잡는지는 백엔드의 `fileKey`에 달렸다:

| 백엔드 | `fileKey` | 라이브러리 순환 감지 |
|---|---|---|
| 로컬·루트 | `st_dev`+`st_ino`(`linux/LinuxFileAttributes.kt:50`) | 잡는다 |
| SMB | 경로+서버 `fileId`(`smb/SmbFileAttributes.kt:51`) | 서버가 같은 `fileId`를 주면 잡는다(서버 동작 미확인) |
| SFTP·FTP·WebDAV | 경로 자체(`sftp/SftpFileAttributes.kt:60`, `ftp/FtpFileAttributes.kt:39`, `webdav/WebDavFileAttributes.kt:47`) | 못 잡는다(링크 경로가 늘 다르다) |

오너는 순환 방지를 "깊이 제한으로만" 정했다(2026-11-04). 위 표대로 SFTP·FTP·WebDAV에서는 깊이 제한 말고는 막을 방법이 없다.

| 용어 | 뜻 |

## 2. 오너 결정이 필요한 점 (제안)

### 2.1 Q1 — '폰'의 경계
경계는 **경로마다** 정하고, 복사 한 번은 "원본 항목과 대상 폴더가 모두 폰이면 폰→폰"으로 정한다(압축 풀기는 압축 파일이 있는 곳을 본다).

| 경로 종류(제공자) | 예 | 안 A (추천) | 안 B | 안 C (기존 `isLocalPath`와 같음) |
|---|---|---|---|---|
| 로컬 Linux 경로(`file`, 비루트) | `/storage/emulated/0`, 앱이 Linux 경로로 여는 SD카드·USB(`/storage/XXXX-XXXX`) | 폰 | 폰 | 폰 |
| 같은 경로를 루트로 접근(`RootableFileSystemProvider`) | `/data`, `/system` | 폰 | 폰 | 폰 |
| 문서 제공자 중 기기 저장소(`com.android.externalstorage.documents`, 버그 리포트) | SAF로 연 SD카드·USB | 폰 | 폰 | 폰 |
| 문서 제공자 중 MTP(`com.android.mtp.documents`) | USB로 연결한 카메라·다른 폰 | **네트워크**(다른 기기) | 폰 | 폰 |
| 그 밖의 문서 제공자 | Google Drive, Nextcloud 등 SAF 앱 | 네트워크 | 폰 | 네트워크 |
| 압축 파일 안(`archive`) | 폰에 있는 zip 안 | 압축 파일이 폰에 있으면 폰 | 폰 | 네트워크(`isLocalPath`가 거짓) |
| content URI(`content`) | 다른 앱이 공유한 파일 | 네트워크(출처를 알 수 없다) | 폰 | 네트워크 |
| SFTP·SMB·FTP(S)·WebDAV(S) | NAS | 네트워크 | 네트워크 | 네트워크 |

- 근거 코드: 제공자 목록 `provider/FileSystemProviders.kt:20-33`, 기존 '로컬' 판정 `filelist/PathExtensions.kt:24-29`(Linux 경로 또는 `DocumentResolver.isLocal`), 기기 저장소 제공자 목록 `provider/document/resolver/DocumentResolver.kt:46-50`(MTP 포함).
- **안 A 추천 이유**: 오너 문장 "폰에서 폰으로가 아니면 다 원격"을 '이 기기의 저장소'로 읽는다. MTP는 USB로 붙은 다른 기기라 원격에 가깝다. 압축 파일은 그 파일이 있는 곳을 따른다(폰의 zip 풀기에서 링크가 링크로 풀린다 — `cp`·`unzip` 기본과 같다).
- 안 B는 "앱이 기기 안에서 보는 것은 모두 폰"으로 단순하지만 Drive 같은 클라우드도 폰이 된다. 안 C는 기존 판정을 그대로 쓰지만 폰의 zip 풀기가 네트워크 복사가 된다.
- 어느 안이든 **링크가 실제로 생기는 곳**은 로컬·루트·SFTP·SMB 원본과 압축 파일 안뿐이다(1.4 표). 문서 제공자·content URI는 링크가 없으므로 이 경계는 속성 규칙(수정 시각)에만 영향을 준다.

### 2.2 Q2 — 순환을 막는 깊이 제한
오너 결정: 깊이 제한으로만 막는다. 무엇을 세는지와 값을 정해야 한다.

| 안 | 세는 것 | 값 | 순환이 있을 때 (링크 하나가 자기 부모를 가리키면) | 정상 복사에 주는 영향 |
|---|---|---|---|---|
| **A (추천)** | 링크 깊이(지금 항목까지 따라간 링크 수) | **8** | 폴더가 8번 겹쳐 복사된 뒤 그 링크가 실패한다 | 링크가 9번 겹친 정상 구조만 실패. 링크 없는 깊은 폴더는 영향 없음 |
| B | 링크 깊이 | 40(리눅스가 경로 하나를 풀 때 허용하는 링크 수 `MAXSYMLINKS`와 같은 값) | 40번 겹쳐 복사된다 | 사실상 없음 |
| C | 복사 시작점부터의 폴더 깊이 전체 | 64 | 시작점 깊이에 따라 최대 64번 겹친다 | 링크 없이 64단보다 깊은 폴더도 실패한다(`cp` 기본에는 없는 제한) |

- **피해 규모**: 깊이 제한은 순환을 '끊을' 뿐 순환 전까지의 복사를 막지 못한다. 자기 부모를 가리키는 링크가 한 폴더에 둘 있으면 복사량이 대략 2^제한값 배로 늘어난다(A: 256배, B: 2^40배 — 사실상 끝나지 않음). 그래서 값을 작게 잡는 A를 추천한다.
- **라이브러리 순환 감지(1.4)**: 링크를 따라가는 순회에 라이브러리를 쓰면 로컬·SMB에서는 라이브러리가 먼저 순환을 잡는다. 오너의 "깊이 제한으로만"을 '깊이 제한이 반드시 있어야 하는 유일한 장치'로 읽어, 라이브러리가 잡은 순환도 같은 실패(그 링크 실패, 나머지 계속)로 처리하는 것을 추천한다. 라이브러리 감지를 일부러 끄려면 순회를 직접 짜야 한다(HLD에서 비용 비교).

### 2.3 Q3 — 폰→폰의 '속성'
오너의 두 문장이 글자 그대로는 다르다.
- "로컬 파일을 복사할 때는 속성을 맞출거야"(2026-11-04, 이슈 본문)
- "cp의 기본동작"(같은 날). 글자 그대로의 `cp`(옵션 없음)는 권한만 원본에서 가져오고(umask 적용, setuid 등은 빠짐) 수정 시각·xattr은 맞추지 않는다.

| 안 | 폰→폰 복사 결과 | 코드 영향 | #48 |
|---|---|---|---|
| **A (추천)** 지금 동작 유지 | 권한·수정 시각을 원본에 맞춘다(지금과 같음) | 폰→폰 경로는 고치지 않는다 | 그대로 유효(일시정지 유지, 오너 결정 뒤 처리) |
| B 글자 그대로의 `cp` | 수정 시각 = 복사한 시각, xattr 안 옮김 | `LinuxCopyMove.kt:199-224`와 `ForeignCopyMove`의 폰→폰 경우를 바꾼다(조각 하나 추가) | 해당 코드가 없어지므로 #48은 할 일이 없어진다 |

추천 이유: 오너가 속성을 맞춘다고 직접 말했고, 요구사항 정리 v1 1번도 링크만 말한다. "cp 기본"은 '링크를 링크로 둔다'는 뜻으로 읽는다.

### 2.4 Q4 — 이동에도 적용하는가
이동은 같은 제공자 안이면 이름 바꾸기(`moveAtomically`, `FileJobs.kt:1240-1242`)로 끝나고, 안 되면 복사 후 원본 삭제다(1171-1225). 지금 이동은 `COPY_ATTRIBUTES`로 소유자까지 맞춘다.

| 안 | 내용 | 영향 |
|---|---|---|
| **A (추천)** 이번에는 복사만 | 이동은 지금 동작 그대로. 필요하면 별도 이슈 | 폰→NAS 이동에서 링크는 지금처럼 SFTP·SMB에 링크로 만들어지고 FTP·WebDAV에서는 실패한다. 그래서 #47 뒤 쓰이지 않을 것으로 본 SFTP·SMB 링크 분기(#47 HLD 6절)는 **이동 때문에 계속 쓰인다** — 지울 수 없다(조각 D 참고) |
| B 이동에도 적용 | 네트워크 이동도 링크를 따라가고 속성을 맞추지 않는다 | 따라간 링크를 이동한 뒤 원본을 지울 때 **링크만** 지우고 링크가 가리키던 실제 데이터를 지우지 않아야 한다는 요구가 새로 생긴다. 위험이 커서 별도 조각·검수가 필요하다 |

## 6. 비기능 요구사항
- **API 레벨**: minSdk 그대로. 새 라이브러리 없음.
- **권한·루트**: 새 권한 없음. 루트로 여는 경로는 비루트 로컬과 같은 분류(폰).
- **성능**: 네트워크 복사의 링크 따라가기는 항목마다 왕복이 늘 수 있다(따라간 속성 읽기). 링크가 없는 항목에 왕복을 더하지 않는 것을 권장한다(HLD에서 확인).
- **오류 표시**: 새 오류(깊이 제한)는 기존 복사 오류 창으로 보인다. 새 문자열이 필요하면 영어·한국어만 더하고 다른 로캘은 영어로 대체된다(#21 일시정지).
- **시험 환경**: 실제 NAS가 없으면 서버 동작은 PR에 "미확인"으로 적는다. 오너 기기 설치는 사전 승인이 필요하다.

## 7. 제약과 가정
- 링크를 따라간 뒤 대상 서버·제공자가 정하는 수정 시각은 '복사한 시각'으로 본다(서버 시계 차이는 다루지 않는다).
- FTP의 링크 따라가기(`ftp/client/Client.kt:262-263`)는 링크 대상 문자열을 링크 경로 자신에 붙인다(`path.resolve`). 상대 경로 링크면 잘못된 경로가 될 수 있어 보인다(코드 읽기, 미확인). 조각 B의 범위에서 HLD가 확인한다.
- WebDAV에는 파일 시스템 링크가 없고 '링크'는 HTTP 이동 응답이다. 조각 B의 따라가기는 HTTP 클라이언트의 이동 처리에 기대며, 실제 동작은 HLD에서 확인한다(미확인).
- Samba 등 SMB 서버는 서버 쪽 유닉스 링크를 스스로 따라가 일반 파일·폴더로 보여 주는 경우가 많다(서버 설정에 따름, 미확인). 이때 앱은 링크를 보지 못하고 이 SRS와 같은 결과가 된다.
- 깊이 제한은 순환을 끝낼 뿐, 제한까지의 중복 복사는 막지 못한다(2.2 피해 규모). 오너 결정(깊이 제한으로만)에 따른 알려진 동작이다.

| D2 | 원본 확인을 할 수 없는 경로는 지우지 않고 실패(새 선택지 없음) | 사용자에게 "먼저 지우고 계속할까요?"를 묻는다 | 코드 읽기로는 모든 네트워크 경로가 원본을 먼저 열 수 있다(FTP도 연결 풀로 원본·대상 연결을 따로 쓴다, `ftp/client/Client.kt:41-76`). 물을 경우가 실제로 없으면 창을 바꾸지 않는 편이 #54와 충돌이 없다. 실제 사례가 나오면 #54와 함께 선택지를 정한다 |
| D3 | 분류는 복사 항목(시작 항목) 단위로 한 번 하고 하위 항목은 물려받는다 | 하위 항목마다 판정 | 한 복사 안에서 규칙이 섞이지 않는다. 하위 항목은 시작 항목과 같은 제공자다(링크를 따라가도 같은 제공자 안) |
