## 1. 목적과 범위

### 1.1 목적
앱이 백그라운드에 있는 동안 **시스템이** 앱 프로세스를 종료한 뒤, 사용자가 최근 앱 목록 등으로 돌아왔을 때 각 창이 종료 전에 보던 경로에서 다시 열리게 한다. 규격 필수 조항 `State_Preservation`의 등록 편차(`docs/STANDARDS_TRACEABILITY.md` 3장, 해소 이슈 #11)를 해소한다.

### 1.2 지금 동작 (근거)
- 창의 경로·이동 기록은 창 뷰모델 `FileListViewModel`의 `TrailLiveData`에만 있다(`FileListViewModel.kt:27`). 뷰모델은 저장 상태를 쓰지 않는다(`FileListViewModel.kt:25` `// TODO: Use SavedStateHandle to save state.`). 뷰모델 팩토리도 저장 상태 핸들을 받지 않는다(`util/FragmentViewModelLazy.kt:15-31`, `CreationExtras`를 쓰지 않는 팩토리).
- 시스템이 프로세스를 종료한 뒤 화면을 복원하면 액티비티·호스트·두 창 프래그먼트는 FragmentManager가 다시 만들지만(`FileListActivity.kt:31-36`, `FileListHostFragment.kt:134-145`) 뷰모델은 새로 생긴다. 그래서 `viewModel.hasTrail`이 거짓이 되어 처음 시작과 같은 시작 경로 결정을 다시 탄다(`FileListFragment.kt:274-335`: Intent 경로·압축 루트·`ACTION_VIEW_DOWNLOADS`, 없으면 `Settings.FILE_LIST_DEFAULT_DIRECTORY` `:329`).
- 회전·크기 변경 같은 구성 변경에서는 뷰모델이 살아 있어 경로가 유지된다(이슈 #2 REQ-2-04, 지금도 충족).

### 1.3 용어
| 용어 | 뜻 |
|---|---|
| 시스템 종료 후 복원 | 사용자가 화면을 닫지 않았는데 시스템이 프로세스(또는 "활동 보관 안함" 개발자 옵션에서 액티비티)를 없앤 뒤, 사용자가 그 화면으로 돌아와 시스템이 저장 상태로 화면을 다시 만드는 경우. 이때 화면은 저장 상태(`savedInstanceState`)를 받지만 창 뷰모델은 새로 생긴다. |
| 새로 시작 | 저장 상태 없이 화면이 처음 만들어지는 경우: 실행기 아이콘, 최근 앱에서 지운 뒤 다시 열기, 뒤로 가기로 화면을 끝낸 뒤 다시 열기, 다른 앱이 경로로 열기(새 화면 인스턴스, #2 HLD 3.7). |
| 구성 변경 | 회전·분할 화면 크기 변경 등으로 액티비티만 다시 만들어지고 뷰모델은 유지되는 경우. |
| 창의 경로 상태 | 창의 현재 경로(Q1 결정 A). 이동 기록(`TrailData`의 `trail`·`currentIndex`, 단계별 스크롤 상태)은 포함하지 않는다. |
| 이동 기록 | 이 앱의 "뒤로 가기 기록"은 브라우저식 방문 목록이 아니라 경로 표시줄의 단계 목록 `TrailData`다(`TrailData.kt:13-17`). 뒤로 가기는 한 단계 위로 간다(`FileListFragment.kt:254-262` → `TrailData.kt:44-50`). 상위로 올라가도 아래 단계는 목록에 남아 경로 표시줄에서 다시 누를 수 있고, 단계마다 목록 스크롤 위치가 저장된다(`TrailData.kt:18-42`). |

### 1.4 범위
- 범위 안: 파일 목록 화면(`FileListActivity`)의 각 창(두 창 사용 시 창 1·창 2, 선택 모드면 창 1만)의 경로 상태를 시스템 종료 후 복원 때 되살리기. 복원한 경로에 접근할 수 없을 때의 처리. 편차 등록부 갱신.
- 범위 밖:
  - 앱 재시작 후 경로 기억(영구 저장) — 오너가 거절(요구사항 정리 v1 범위 밖, #2 REQ-2-18).
  - 검색 상태·선택 상태·보기 방식 등 경로 외 창 상태의 복원(A3).
  - 다른 화면(편집기·뷰어·설정 등)의 상태 복원.
  - 복사 목록(프로세스 전역, #2 HLD 3.1 K8)의 복원.

## 3. 비기능 요구사항
- **지원 API**: minSdk 23 ~ targetSdk 36(`app/build.gradle:34,37`). API 수준에 따라 다른 동작을 두지 않는다.
- **성능**: 저장은 창 경로가 바뀔 때 또는 상태 저장 시점에 경로 값(창마다 `Parcelable` 한두 개)만 담는다. 복원 판단은 메인 스레드에서 즉시 끝나야 하고(입출력 없음, REQ-11-06), 목록 읽기는 기존처럼 비동기다.
- **저장 크기**: 저장 상태 묶음은 Binder 거래 한도(약 1MB, 화면 전체 공유)를 넘지 않아야 한다. Q1 A(현재 경로만)라 창마다 경로 하나와 호스트의 활성 창 번호 하나뿐이어서 문제없다.
- **권한**: 새 권한 없음. 복원 자체는 새 권한 요청을 만들지 않는다. 루트 경로 복원 시 루트 사용 여부·권한 요청은 기존 루트 접근 규칙을 그대로 따른다. 저장소 권한 안내는 지금처럼 동작한다 — 진행 상태 `isStorageAccessRequested`가 호스트 뷰모델에 있어 프로세스 종료 뒤 처음 값이 되므로 권한이 없으면 `onResume`에서 안내가 다시 뜰 수 있다(`FileListHostFragment.kt:236-245`·`:359-382`, 지금과 같음).
- **루트/비루트·원격·압축**: 경로 종류에 따라 복원 규칙을 나누지 않는다. 접근 실패는 REQ-11-05로 알린다.
- **오프라인**: 원격 경로 복원 시 네트워크가 없으면 REQ-11-05의 실패 표시. 앱이 멈추지 않는다.
- **접근성**: 새 UI 요소 없음. 실패 표시는 기존 오류 문구를 쓴다(기존 접근성 수준 유지).
- **개인정보**: 저장 상태는 시스템이 앱 프로세스 밖(시스템 서버)에 잠시 보관한다. 경로 문자열 외에 원격 저장소 비밀번호 같은 인증 정보를 저장 상태에 넣지 않아야 한다(원격 경로의 인증 정보는 기존처럼 저장소 설정에서 다시 얻는다, `app/AppInitializers.kt:73-76`).

### 4.2 검증 절차 (수동, 에뮬레이터)
오너 기기에는 알리지 않고 설치하지 않는다. 에뮬레이터(API 23 하나, API 34 이상 하나 권장)에서 한다. 패키지 이름은 `me.zhanghai.android.files`(`app/build.gradle:33`).

| ID | 절차 | 확인하는 것 |
|---|---|---|
| V1 | `adb shell settings put global always_finish_activities 1`("활동 보관 안함" 켬) → 앱에서 창을 옮김 → 홈 → 최근 앱에서 복귀 → 끝나면 `... always_finish_activities 0` | 액티비티 재생성 + 새 뷰모델(A2). 가장 빠른 반복 확인. |
| V2 | 앱에서 창을 옮김 → 홈(앱이 백그라운드여야 함) → `adb shell am kill me.zhanghai.android.files` → `adb shell pidof me.zhanghai.android.files`(API 23은 `adb shell ps | grep me.zhanghai.android.files`)로 프로세스가 없는지 확인 → 최근 앱에서 복귀 | 실제 시스템 프로세스 종료 후 복원. (Android Studio Logcat의 "Terminate Application"도 같다.) |
| V3 | 앱에서 창을 옮김 → 최근 앱에서 앱을 지움(또는 뒤로 가기로 화면 종료) → 실행기에서 다시 열기 | 새로 시작(REQ-11-03). |
| V4 | 회전·분할 화면 크기 변경 | 구성 변경 비회귀(REQ-11-07). |

V2가 정본이다. V1은 프로세스가 살아 있어 프로세스 전역 상태(복사 목록 등)의 영향이 가려지므로 빠른 반복 확인용으로만 쓰고, 통과 판정은 V2로 한다. `adb shell am force-stop`은 사용자가 강제 종료한 것으로 보아 쓰지 않는다(시스템 종료 재현이 아님).

### 4.3 확인이 필요한 점 (오너·PM 결정)

**Q1. 이동 기록까지 복원할지 — 결정: A (오너, 2026-11-19, issuecomment-6999035882)**

먼저 사실: 현재 경로만 복원해도 `TrailData.of(path)`가 상위 단계를 모두 만들므로(`TrailData.kt:59-82`) 뒤로 가기로 상위 폴더로 올라가는 동작은 종료 전과 같다. 차이는 종료 전에 상위로 올라와 있던 경우 경로 표시줄에 남아 있던 **아래 단계**, 그리고 **단계별 스크롤 위치**뿐이다.

| 안 | 내용 | 비용 | 사용자가 잃는 것 |
|---|---|---|---|
| A (권고) | 현재 경로만 | 가장 작음 — 창마다 경로 하나 저장, `TrailData` 형식 변경 없음 | 경로 표시줄의 아래 단계, 단계별 스크롤 위치. **현재 폴더의 스크롤 위치도 잃을 수 있다(미확인)**: 스크롤 위치는 폴더를 옮길 때 뷰모델의 `TrailData`에 담기고(`FileListFragment.kt:946`) 목록이 다 읽힌 뒤 `pendingState`로 되살리는데(`:791`), 프로세스 종료 뒤에는 새 뷰모델이라 이 값이 없다. 프래그먼트 뷰 상태 복원이 비동기로 채워지는 목록의 위치를 되살리는지는 HLD에서 확인한다. |
| B | 경로 표시줄 단계 목록 + 현재 위치(`trail`·`currentIndex`) | 작음~중간 — `TrailData`를 저장·복원할 형식 추가, 단계 수만큼 저장 크기 증가, 저장 형식 시험 | 단계별 스크롤 위치 |
| C | B + 단계별 스크롤 위치(`states`) | 중간 — B에 더해 단계마다 목록 뷰 상태를 저장(크기 상한 필요), 대기 상태 소비 규칙(`TrailData.kt:52-53`)과의 맞물림 확인 | 없음 |

권고: **A**. 뒤로 가기 동작은 A로도 같고, 규격(부록 S)은 "규격을 만족하는 최소 변경"을 요구하며, `State_Preservation`은 오래 떠나 있던 경우 첫 화면 시작까지 허용하므로 현재 경로 복원으로 충족된다고 판단한다(조항 해석은 오너 승인 사항). B·C는 나중에 따로 더해도 A의 저장 구조를 버리지 않는다.

**Q2. 복원 때 접근할 수 없는 경로의 처리 — 결정: 가 (오너, 2026-11-19, issuecomment-6999035882)**

| 안 | 내용 | 비용 | 장단점 |
|---|---|---|---|
| 가 (권고) | 그 경로에서 열고 오류 표시 | 거의 없음 — 지금 실패 표시(`FileListFragment.kt:755-782`)를 그대로 씀 | 사용자가 어디였는지 보이고, 네트워크가 돌아오면 새로 고침으로 바로 이어진다. 뒤로 가기·경로 표시줄로 언제든 옮길 수 있다. "막지 않고 알린다"(12장)에 그대로 맞는다. 다만 원격 서버가 응답하지 않으면 목록 자리에 연결 시간 초과까지 로딩이 보인다(기존 탐색과 같음). |
| 나 | 가장 가까운 읽을 수 있는 상위 폴더로 | 큼 — 복원 시 상위로 올라가며 접근을 확인하는 백그라운드 탐색, 원격이면 상위도 모두 실패해 결국 다른 규칙이 또 필요, 옮겼다는 알림 추가 | 바로 쓸 수 있는 목록이 보이지만 실패 원인이 가려지고(옮긴 이유를 따로 알려야 함), 일시적 네트워크 끊김에도 위치를 잃는다. |
| 다 | 기본 디렉터리로 + 알림 | 중간 — 실패를 감지한 뒤 창을 기본 디렉터리로 옮기는 흐름과 알림 문구(번역 포함) 추가 | 지금 동작에 가깝지만 일시적 실패에도 위치를 잃고, 복원의 의미가 줄어든다. |

권고: **가**. 실패를 감추지 않고 알리며, 새 메커니즘이 없고, 일시적인 실패(네트워크·루트 응답 지연)에도 위치를 잃지 않는다.

**Q3. 활성 창도 복원할지 — 결정: 복원한다 (오너, 2026-11-19, issuecomment-6999035882) → REQ-11-09**
지금 프로세스 종료 뒤에는 활성 창이 항상 창 1이 된다(`DualPaneViewModel.kt:10`, #2 HLD 3.1). 폰 세로(한 창 모드)에서 창 2를 보다가 종료되면, 경로는 복원돼도 복귀 화면에는 창 1이 보여 사용자는 "보던 폴더가 아니다"라고 느낄 수 있다. 활성 창 번호(정수 하나)를 함께 복원하는 비용은 작다. v1.1에서는 요구사항 1이 "각 창의 현재 경로"만 정해 넣지 않았고 설계팀 권고는 넣는 것이었다(보이는 화면이 종료 전과 같아야 `State_Preservation`의 "최대한 그대로"에 맞다).
